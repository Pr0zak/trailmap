# CLAUDE.md — trailmap

Personal Android app (Pixel 9a) that shows nearby walking/biking trails — paved, gravel, dirt —
on a map, colored by surface. Test location: **Kansas City** (39.0997, -94.5786).
Single-user, personal. App-only (no backend): the phone talks to OpenStreetMap + elevation APIs directly.

## Self-update (in-app)
`update/UpdateChecker.kt` polls the **GitHub Releases API** (`/repos/Pr0zak/trailmap/releases/latest`) on launch, compares the `app-v*` tag to `BuildConfig.VERSION_NAME`, and if newer shows a dialog (in `MainActivity.UpdateGate`) → downloads the APK to externalCache → installs via FileProvider + `ACTION_VIEW` (needs `REQUEST_INSTALL_PACKAGES` + the `${applicationId}.fileprovider` provider). `versionName` defaults to the repo `VERSION` file locally (CI overrides with `-Pversion.name` from the tag). **Testing caveat:** a debug-signed build can't install a release-signed downloaded APK (signature mismatch) — the installer launches but the final install fails; production is release→release (same keystore) so it works. To test the *prompt+download*, build debug with `-Pversion.name=0.1.0` so it sees the latest release as newer.

## Stack
- **Kotlin / Jetbrains Compose**, Material 3, **MapLibre GL Native 11.5.2** (keyless raster basemap).
- OkHttp + kotlinx-serialization (no Retrofit). Location = fused (`play-services-location`) **with a `LocationManager` fallback** (so device/emulator GPS works even without Play Services), then a Kansas City fallback.
- Kotlin 2.0.20, AGP 8.5.2, compileSdk 35, minSdk 26. App module under `mobile/`.

## Modes & filters (TrailsViewModel.TrailsUiState)
- **Load-on-pan** — the map refetches as you scroll. `MapScreen`'s camera-idle listener calls `vm.onCameraIdle(bounds, center)`; `needsRefetch` fires on **distance moved**, never on whether the loaded circle covers the screen. That distinction is the whole ballgame: past about z9 the screen is 166 km across and the widest circle the app will fetch is 24 km, so a coverage test can never be satisfied and fires on *every camera idle* — an on-device log caught three refetches in two seconds, each cancelling the last mid-download. That is what made the map perpetually say "Loading trails", and how the app earned a per-IP block. The threshold scales with the loaded radius (`MIN_DRIFT_FRACTION`) and, once the screen is wider than that circle, with the screen (`WIDE_DRIFT_FRACTION`), so the cadence stays proportional to how much ground a pan covers. Debounced 450 ms (120 ms when the area is already parsed in memory). Before scheduling, `onCameraIdle` asks `overpass.cachedCircleFor()` whether the fetch would simply hand back the circle already loaded, and skips it if so — otherwise it livelocks: the gate measures distance from the loaded circle's *centre*, a cached circle keeps its own centre however far the map wanders inside it, so once past the threshold every idle re-reads the same file. A device log caught nine such loads in thirteen seconds, each a cache hit returning identical data. A load whose served circle is unchanged also leaves `trailsVersion` alone, sparing a pointless GeoJSON rebuild.
- **The map draws a union, not the last load.** `loadedAreas` holds up to `MAX_LOADED_AREAS` (10) circles bounded by `MAX_RETAINED_VERTICES` (200,000 polyline vertices, ~14 MB retained), and `ui.trails` is their deduped union with distances re-measured from the current map centre. Areas are **mode-tagged**: ALL and MTB are different datasets over the same ground, and `unionFor()` draws only the current mode's — `setMode` re-scopes the drawn set immediately rather than waiting for the load, since an MTB switch whose fetch timed out otherwise sat there showing paved greenways under a legend headed "Difficulty". **Eviction is by mode first (the other mode's circles are holding budget, not being drawn) then by distance from the viewport, never by age** — age-based eviction made the map collapse from 400 trails to 100 as panning through empty country pulled in circles holding 13, 5 and 57 trails, each displacing part of the dense 302-trail metro circle. Replacing the set on every load meant *zooming out removed trails*: the wide cached circle on screen got swapped for a fresh 16 km one, a dot in the middle of an 89 km view — a device log caught it dropping from 302 trails to 38. Newest wins on an id collision, since the same named trail pulled inside a wider circle carries more of its member ways.
- `bootstrap()` awaits a location fix before it can call `load()`, so until then there is no pending circle for the gate to measure against and the first camera idle would start a second load. `bootstrapPending` suppresses camera-driven loads for that window. One load is capped at `LOAD_BUDGET_MS` (25 s) across every mirror and retry — with all three mirrors down a load was observed hanging for 80 s. Loads supersede each other (`loadJob.cancel()` + a `loadSeq` guard) and the HTTP call is cancelled with them. The **camera is decoupled from `ui.center`** — its start position is handed to `MapView` via `MapLibreMapOptions.camera(...)` **in the AndroidView factory**, restored from `vm.lastCamera` after a tab switch, and only my-location / trail-system headers move it afterwards. Constructing `MapView(c)` bare is a trap: MapLibre starts at 0,0 / zoom 0 and reports a camera-idle from there before any effect can move it, which overwrote `lastCamera` with the whole world — so every tab switch or detail round-trip dropped the user onto a blank global map. `onCameraIdle` also refuses to record a camera below `MIN_RECORDABLE_ZOOM`. Following `ui.center` instead following `center` would likewise yank the map back and re-trigger the fetch it just answered. The **"Load trails as I pan"** switch in the Filters sheet (persisted) turns pan-loading off; **"Search this area"** appears when the view is too wide to auto-cover (`canAutoCover`). How much to **download** is deliberately decoupled from the radius chip, which only says how much to **list**: `fetchRadiusFor` clamps every ALL-mode fetch into `MIN_FETCH_RADIUS`..`MAX_AUTO_RADIUS`, currently both **16 km**. That size is chosen for reliability, not coverage: on-device logs put a 16 km named-way pull at ~1.45 MB returning in 3-7 s every time, against 3.1-3.8 MB at 24 km — which is what timed out on a flaky mirror. Fetching only the 5 mi chip meant one flick-pan left the loaded circle and paid for another round trip; a named-way pull at 16 km is ~1.4 MB and covers a lot of panning. Measured: one 16 km fetch then five pans with **zero further requests**. MTB mode opts out of viewport-derived radii ("systems within 25 mi" is a search radius, not a description of the screen).
- **MapMode.ALL** — paved/gravel/dirt **off-road trails/paths only** (highway path/cycleway/track/bridleway + non-sidewalk footway), default ~5 mi radius, selectable **3 / 5 / 10 mi**. Deliberately **excludes streets + sidewalks**: `route=bicycle` relations were tried but dropped because most are on-street bike routes (drew lines over roads). Off-road bike *paths* are still captured as standalone `cycleway` ways.
- **Trail selection:** tapping the map selects the nearest trail (a padded box query, so taps *near* a thin line register) → shows a peek card + a yellow highlight glow layer. Nothing is auto-selected at startup. The list / system headers drive the map separately. The peek card has Save, Details, Add to ride and a close (✕). The legend + buttons row and the card share one bottom column in `MapOverlays`, so the card pushes the controls up by its real height (no hard-coded offsets), and the column's bottom padding clears the MapLibre attribution. Likewise the status pill sits in a column under the search bar — the old fixed 108 dp offset put the loading pill on top of the chip rows.
- **MapMode.MTB** — mountain-bike trails only, default 25 mi radius, selectable **10 / 25 / 40 mi**. Shows OSM `mtb:scale` difficulty badges (S0 Beginner → S6 Extreme, `MtbDifficulty`). The Trails list **clusters** trails into systems/parks (`clusterTrailSystems`, union-find by ~2.5 km centroid proximity) under headers, **named after the enclosing OSM park** (a second `leisure=park|nature_reserve|…` / `boundary=protected_area` query + point-in-polygon on each trail's center → e.g. "Kessler Park", "Swope Park"); falls back to the member-name common prefix, else the longest member, when no park contains them. Map lines are colored by difficulty (rated) or surface (unrated). A **legend** card keys the colors (difficulty in MTB, surface in ALL).
- **Filters** (apply to map + list, via `.filtered`): surface (paved/gravel/dirt), use (walk/bike), **min-length** (Any/1+/3+/5+/10+ mi), **name search** (substring), and a permanent **named-only** filter (drops "Unnamed path" connectors). Both the map and the Trails list use one **search bar** (`TrailSearchBar` in `ui/FilterSheet.kt`: name search, All/MTB toggle, a Filters button whose badge is `activeFilterCount`), and everything else — radius, length, surface, use, the auto-load switch, Reset (`vm.resetFilters`) — lives in the **Filters sheet**. This replaced two rows of 13 chips; the user decided the sheet is enough, so don't add per-surface chips back to the list. The list also has **Sort** (`TrailSort`: distance/length/name, applied in `listed` only — the map ignores it).
- **Dark mode**: the basemap follows the system theme — both basemaps are **OpenFreeMap vector styles** — light = `liberty`, dark = `dark` (keyless, no usage limits, fine to download for offline). CARTO dark_all went key-only (every tile an "API KEY REQUIRED" placeholder) and OSM's raster tiles, the old light map until 0.17.0, forbid the bulk downloading an offline area is. `TrailmapTheme` also sets the status/nav bar icon colour, which nothing did before — white icons vanished over the light map; surface line colors brighten on dark and every line gets a casing so it pops on either basemap. A **Layers** FAB on the map opens a Match system / Light / Dark menu (`vm.setMapTheme`, persisted in `Prefs`), and that choice themes **the whole app** (`MainActivity` feeds it to `TrailmapTheme`), not only the basemap. `ui/theme/Theme.kt` sets every color role for light and dark; leaving container/surface roles unset is what made cards and chips Material's default lavender. Badge fills (`MtbDifficulty.color`, `SurfaceBadge`) are chosen for ≥ 4.5:1 label contrast (dark text on gravel gold); map **line** colors are separate and brighter — `MTB_LINE_COLORS` / `SURFACE_LINE_COLORS` in `MapScreen.kt` drive both the lines and the one-line legend, so they can't drift apart again (the old legend showed 4 of the 7 grades).
- **Saved trails** (star on list rows + detail; persisted in `Prefs`; a "saved only" toggle in the Trails app bar), **Share / Open-in-Maps** on the detail screen (geo: + maps URL intents), and **tappable MTB system headers** (recenter the map on that park via `vm.focusOn` + tab switch).
- **Offline maps = basemap tiles only** (`offline/OfflinePacks.kt` + `ui/OfflineScreen.kt`, the map's cloud FAB): download the **current view** (`ui.viewBounds`, zoom ≤ 14) or a **preset region** (KC Metro / Lawrence / Columbia / Springfield / St. Louis / MO+KS overviews), see progress, **retry**, **delete**. Tile cap 50k; downloads auto-retry transient errors. **Trails come from the state packs, not from here**: downloading an area calls `vm.addPackStatesFor(bounds, overview)`, which adds the packs of every state the box touches (`TrailPacks.statesIn`, a 5×5 point grid — so St. Louis brings Illinois and KC Metro brings Kansas + Missouri; a *state overview* only takes the state it is centred on, since its rectangle clips half a dozen neighbours) and keeps "adding … trails" on the status line through the download. Each area shows "trails on this phone" (`vm.areaTrailsOnPhone`: 9 points all `packCovers`) or offers **Add trails**. Up to 0.16.0 each area also pulled its own trail data from Overpass via a WorkManager job (`TrailDownloads`, removed in 0.17.0 with its foreground-service/notification permissions); that data (`filesDir/overpass`, the durable dir) is still **read** by `coveringCache` but never written, and an "Old trail downloads · Clear" card shows while it exists. Areas downloaded with a style the app no longer draws (`OfflinePacks.isCurrentStyle`) are labelled "old map style — delete and download again". The MapLibre `getStatus`/`OfflineRegionStatusCallback` params are `@Nullable` (override with `OfflineRegionStatus?`/`String?`).
- **Rides** (`ui/RidesScreen.kt` + `ui/RideDetailScreen.kt`, Rides tab — the **Planned** half; **Recorded** is myvitals, see *Your activity*): combine trails into a named ride to see **total length** + trail count + surface breakdown. "Add to ride" lives on the trail detail (creates/append). `Ride`/`RideTrail` are serializable snapshots persisted in `Prefs` (JSON); ride totals work offline / across areas. ViewModel: create/add/remove/rename/delete, `moveTrailInRide` (drag a row's handle to reorder), and `showRideOnMap`, which highlights every trail in the ride (`ui.highlightedRideId`, drawn by the map's highlight layer) and frames them. `RideTrail` records `lat`/`lon` of each trail's centre so the map knows where to go; rides saved before 0.12.0 lack it and only highlight once their trails are loaded. "Add to ride" (`AddToRideDialog`, in `RidesScreen.kt`) is on the trail detail and the map's peek card. Bottom nav is now **3 tabs: Map / Trails / Rides**.

## Your activity (myvitals, optional)
[myvitals](https://github.com/Pr0zak/myvitals) is the owner's self-hosted health tracker; it already holds every recorded ride/walk with its GPS track (Strava, Garmin FIT imports, Fitbit, Health Connect) and polls RainoutLine for KC trail open/closed status. trailmap reads both — **read-only, from the user's own server, nothing sent elsewhere**. Still "app-only": myvitals is the user's server, not a trailmap backend, and the app works fully without it.
- **Connecting** (`ui/MyVitalsScreen.kt`, route `myvitals`; reached from the Rides tab and the map's Layers menu): server address + **Access key** (the myvitals app's name for it, under Settings → Connection & sync; it is the server's `INGEST_TOKEN` — the only token its `/activities/map` and `/trails` accept besides the dashboard's; both can write, there is no read-only one). The key field has a **Paste** button (`PastedKey.of`: trims the stray newline a copied key tends to carry; "Nothing to paste." on an empty clipboard; refuses inner whitespace, anything outside printable ASCII `!`..`~` or over 4,096 chars with a short message under the field, leaving the field as it was) and is kept in plain `remember`, not saved state, since that Bundle leaves the app. `MyVitalsClient.connect` tries the address and then `<address>/api`, because the dashboard (Caddy :8080) proxies the API under `/api` and people paste either; a 401 stops the search. `MyVitalsClient.get` builds the URL and the `Authorization` header in separate tries, so a key character OkHttp can't send reads "That access key has characters an access key can't contain." (reason `AUTH`, which also stops the `/api` retry) rather than "That isn't a web address." The screen shows a small spinner instead of the form until `MyVitalsUi.settingsLoaded` (set once `loadMyVitals` has read the store) — a handoff at a cold start opens it before that — and `loadMyVitals` carries a generation counter (`settingsGen`, bumped by connect and disconnect) so it never applies settings it read before a newer connect saved new ones. Nothing is saved until a connect succeeds. Plain HTTP on the LAN is why `usesCleartextTraffic` matters. The address is usually a LAN IP, so it only syncs at home or over Tailscale; cached data works anywhere.
- **Handoff from the myvitals app** (`data/MyVitalsHandoff.kt`): its "Send to trailmap" button starts `MainActivity` with action `com.trailmap.action.CONNECT_MYVITALS`, string extras `com.trailmap.extra.MYVITALS_URL` (the address as saved there) and `com.trailmap.extra.MYVITALS_TOKEN` (its access key), a **sender** extra `com.trailmap.extra.MYVITALS_SENDER`, and `setPackage("com.trailmap")` — never an implicit broadcast or chooser. The manifest's filter is that action + `DEFAULT`; `singleTask` means it lands in `onCreate` (only when `savedInstanceState == null`) or `onNewIntent`. **Both directions are pinned.** myvitals only sends to a trailmap signed with trailmap's release certificate (SHA-256 `0aeaa84a18d61fb2b7ae60b7b2d74e40a252c4ab7fbe775162cac21f7bb6b0d4`, public), except its own debug builds, which accept any signature so a debug trailmap can be tested. trailmap only accepts an offer that **myvitals sent**: the sender extra is an immutable `PendingIntent` myvitals creates for itself and never fires; trailmap reads it with `IntentCompat.getParcelableExtra` (wrong type or a malformed Bundle → no sender) and requires `creatorPackage == "app.myvitals"` (filled in by the system, unforgeable) **and** that the installed `app.myvitals` is signed with myvitals' release certificate (`MYVITALS_CERT_SHA256` = `4822db0ca48d34f4ca29388dcfe312dfd4b0631a3adffdd3cda948790851591a`, public) — `hasSigningCertificate(pkg, pin, CERT_INPUT_SHA256)` on API 28+, SHA-256 of `GET_SIGNATURES` (exactly one signer) on 26-27. trailmap **debug** builds skip the certificate but still require the package name. The manifest's `<queries><package android:name="app.myvitals"/></queries>` is what lets the package manager answer on Android 11+. An unverified offer is dropped entirely — no UI, no navigation, one DiagLog line "ignored a connection offer from an unverified app" (no address, no key). The pure parts (`decodeSha256Pin`, `isFromMyVitals(creatorPackage, debug, signedByMyVitals)`, `certificatesMatch`) are JVM-tested; the Android lookups sit behind that lambda. `take` also ignores a Recents relaunch (`FLAG_ACTIVITY_LAUNCHED_FROM_HISTORY` replays the task's first intent), reads the extras in a try, and removes all three from the intent. `parse` trims and rejects blanks, an address over 2,048 chars, a key over 4,096; the **address** must be http/https (a bare `host:port` counts as http; `file:`, `intent:`, `javascript:`, `ftp://`… don't), with no userinfo (`@` before the host) and no control, whitespace or Unicode format (Cf) characters; the **key** must be printable ASCII `!`..`~` only (`MyVitalsClient.isKeyText`). **Confirm before connect**: `vm.offerMyVitals` numbers the offer (`MyVitalsOffer.id`, a sequence seeded from the monotonic clock — an identical re-send is a new offer) and puts it in `ui.myVitalsOffer`; `TrailmapRoot` navigates to `myvitals` when one appears. Not connected → the form arrives filled in (also when the screen is already open) under a "Filled in from the myvitals app" banner that puts the offer's **host** first, big, then the full address; the offer also clears any stale `myVitals.error`. The form remembers the id of the offer it applied (`rememberSaveable`, the id only — never the key), so a new offer, even an identical one, refills fields the user changed, while an activity recreated by a font or locale change doesn't lay the old offer back over them. Already connected → a card with the host and address, **Use this** (`acceptMyVitalsOffer`, which only replaces the working connection if the new one connects) and **Dismiss**; if it fails, the reason shows **in that card** (`ui.myVitalsOfferError`, cleared by Dismiss or a new offer) and the Connected card's "Last try failed" stays for sync failures only. An offer equal to the connection in use (`normalizeUrl(url)` and key both match → `ui.myVitalsOfferCurrent`) shows "Already connected to <host>" with **OK** instead, and nothing reconnects. A successful connect clears the offer it was for; a failed one keeps it so the form stays filled. Back (arrow or gesture) dismisses it. `connect` cancels the sync *and* the conditions loop (an in-flight `/trails` for the old server would overwrite the new one's board) and restarts the loop when it settles. **The key is never logged**: DiagLog gets the host only, and `MyVitalsOffer.toString()` / `MyVitalsSettings.toString()` / `PastedKey.Key.toString()` redact it; the only place it is written is `MyVitalsStore`, after a successful connect.
- **Storage** (`MyVitalsStore`): everything in `filesDir/myvitals/` (settings.json with url/token/apiBase/autoSync/last sync times, tracks.json, conditions.json), written through a temp file. **Excluded from cloud backup and device transfer** (`res/xml/backup_rules.xml`, `data_extraction_rules.xml`). Disconnect deletes the directory. Never put a real address, token or track in the repo — tests and snapshot samples use made-up geometry.
- **Sync** (`TrailsViewModel.sync`): `GET /activities/map?limit=5000` — every GPS activity as an RDP-simplified polyline (1e-4°, ≤400 pts), a few hundred KB vs 10× for `/activities?polyline=full`; matched against full tracks it finds the same ridden trails to within 1%. The whole list each time (catches deletions, retypes, late Health Connect routes). **Cadence**: on app foreground if the last sync is > 1 h old (`AUTO_SYNC_EVERY_MS`), conditions (`GET /trails`) every 15 min while the app is on screen (`CONDITIONS_EVERY_MS`, myvitals' own RainoutLine poll rate), plus **Sync now**; the **Sync automatically** switch off = manual only. `MainActivity` feeds ON_START/ON_STOP to `vm.setForeground`. Failures keep what's on the phone and show on the myvitals screen. RainoutLine links (`TrailStatus.url`) come from the server, so the map's condition card and the detail screen's open only `TrailStatus.link` — the URL when it is http/https and parses — and show no link otherwise.
- **Activity kinds** (`ActivityKind.of`, keyword match on myvitals' provider type strings: `cycling`, `ebikeride`, `mountain_biking`, `outdoor_bike`, `walking`, `hike`, `running`…; indoor/virtual → OTHER). Rides = BIKE/EBIKE/MTB, on foot = WALK/HIKE/RUN. Timestamp-only names ("20260921-221311") are dropped so the kind + date show instead.
- **Matching** (`data/RideMatch.kt`, `TrackIndex`): tracks as segments in a 25 m grid (CSR arrays, ~MBs); each trail is walked in ≤10 m steps and each step asks which tracks pass within **20 m** (`MATCH_M`). A track counts on a trail when it follows **≥ 300 m of it, or half of a shorter trail, never < 60 m** — so crossings and a block of parallel road don't count. Output `TrailVisits`: ride ids / on-foot ids newest first, last dates, ridden & on-foot metres (union), and `riddenPaths` (the covered stretches). The ViewModel matches whatever the map loads (`scheduleVisits`, keyed on `trailsVersion`), caching per trail id + geometry key per index; on the emulator a 16 km KC load (~175 trails) matches in ~0.2 s against a few hundred tracks. Known limitation: side-by-side paths within 20 m share rides (a horse trail sharing one stretch with a bike loop gets every ride on that loop, at ~20% covered) — the detail page's coverage says how much.
- **Where it shows**: map — a blue glow under ridden stretches (`LAYER_RIDDEN`, "you" blue `YOU_LINE_COLOR`, legend second row), a **My tracks** layer (thin, under everything), a bold single recorded track ("Show on map", banner with ✕), trailhead dots coloured by condition with labels at z ≥ 11 (tap → condition card); Layers menu "Your activity" toggles (persisted in `Prefs.layer`). List rows "Ridden 69× · last Jun 16" / "On foot …"; Filters sheet **Your rides: Any / Ridden / Not ridden yet** (counts in the badge); **Last ridden** sort (only offered when connected; any sort change scrolls the list to the top — keyed LazyColumn rows otherwise keep the old first row in view). MTB system headers "N ridden" + condition line. Trail detail: condition card (unpaved only — `TrailConditions.forTrail` never assigns a status to a paved trail), time **at your pace** (`PersonalPace`: distance ÷ recorded duration incl. stops — tracks have no timestamps, so no per-trail times/segments; last 2 years if ≥ 3 recordings, else all; your usual bike = whichever of bike/e-bike you rode more in the last year; MTB pace on rated or dirt bike trails), "Your rides here" (coverage bar, counts, first/last, the rides). Route preview glows the ridden stretches.
- **Rides tab** is now **Planned | Recorded**. Recorded (`ui/RecordedScreens.kt`) lists activities (All / Rides / On foot); a recorded activity's screen (`recorded/{id}`, id URI-encoded — they contain `:`) loads the trails around its track (packs first, so usually instant/offline), lists the ones it went along **in riding order** (`TrackIndex.trailsAlong`, by earliest matching segment) with how much of each, and offers **Show on map** and **Save as ride** (a planned `Ride` of those trails). Those trails aren't in the map's loaded set, so `trailById` also looks in `auxTrails`.
- **Map framing** (`frame()`, used by Show ride/track on map): MapLibre zoom counts **512-dp tiles** (a phone is ~0.75 tile wide). The old formula assumed 1.6 tiles across and framed everything one zoom level too close.
- Tests: `RideMatchTest` (synthetic geometry: alongside / 40 m road / crossing / half / union / short trail / walks / riding order / perf), `MyVitalsTest` (local HTTP stand-in: direct + `/api` address, bad token, a key character a header can't carry vs a bad address, not-myvitals, unreachable, conditions parse, store round-trip, Paste checks, http(s)-only condition links, pace, condition matching), `MyVitalsHandoffTest` (trimming, blanks, size limits, schemes, userinfo, hidden characters in the address, printable-ASCII keys, pin decoding, the sender decision, pre-28 certificate matching, offer ids vs `sameConnection`, redacted `toString`). Snapshots: `map_you*`, `map_condition`, `map_track`, `list_you`, `list_mtb_you`, `filter_sheet_you`, `detail_you*`, `detail_not_ridden`, `rides_recorded*`, `recorded_ride`, `myvitals_*` (incl. `myvitals_offer`, `myvitals_offer_connected`, `myvitals_offer_error`, `myvitals_offer_current`, `myvitals_loading`).

## Diagnostics
The `OverpassClient` lives on `TrailmapApp` (`TrailmapApp.overpass(context)`), not the ViewModel — a device log showed the ViewModel's `init` running twice at launch, which meant two in-memory parse caches and the same area deserialised twice. Holding it at process scope shares the parse cache, the learned mirror and the rate-limit state across Activity recreation.

Reachable from **Offline maps → the bug icon in the app bar** (and a button lower down). No setup, no key — trailmap has no API keys at all.
`data/DiagLog.kt` is a 500-line in-memory ring, stamped on first use with the build version and device; `ui/DiagnosticsScreen.kt` (Offline maps → **Diagnostics**) shows it newest-first with **Share** and **Clear**. There is no backend to ship logs to and a public repo can't carry an upload token, so the log stays on the device until the user sends it on. Logged: every load's start/duration/trail count, whether each fetch came from memory, disk or the network and what radius it covers, which Overpass mirror answered (with bytes and ms) or how it failed, and the camera-idle decision that triggered a refetch. This is how "why is it slow on my phone" gets answered without an emulator.

## Data sources (all free, keyless)
- **Trail packs, one per state (primary wherever installed).** Public Overpass was measured from KC on 2026-09-26 at 1 success in 6 tries (13.8 s for the 24 km pull; the rest 504 or no answer in 60 s), and the phone log showed pan loads taking 17-25 s or timing out. So `trailpack/build_pack.py` pre-extracts, from Geofabrik state extracts, exactly what the three Overpass queries would return (same filters — keep them in step with `buildQuery`/`buildMtbQuery`/`buildParkQuery`) into a zip of **0.25° tiles** of Overpass `out geom` JSON: `all/`, `mtb/`, `parks/<x>_<y>.json` + `meta.json` (schema, `covered` tiles, and the state's **outline**, padded ~500 m). **Schema 2 stores each element once**: in the tile holding its centre if it's no wider than a tile, else in `<kind>/wide.json`; the app reads a circle's tiles **plus one ring** and the `wide.json` of every state whose bbox the circle reaches (`TrailPacks.tilesFor` / `wideSources`). Schema 1 wrote elements into every tile they touched — the Arizona Trail relation landed in 39 tiles (123 MB of Arizona's 132 MB MTB data), making Arizona 47 MB; schema 2 makes it 13.4 MB, Kansas 1.8 MB, and returns identical elements (checked on 150 random circles). The app reads schemas 1-2 (`TrailPacks.SCHEMAS`); 1 is the 0.15.0 combined pack. **`trailpack/states.txt` is the build list** (50 states + DC; PR/USVI commented out): `.github/workflows/trailpack.yml` runs one matrix job per listed state weekly (and on pushes touching `trailpack/`), uploads `trailpack-<slug>.zip`, then an `index` job merges `trailpack-index.json` (name, size, dates, bbox, coarse outline per state). Deleting/commenting a state in states.txt drops it from the index and **deletes its asset**; a state whose build fails keeps last week's. `workflow_dispatch` takes a `states` subset. All on the **`trailpack` release, a prerelease** — so `UpdateChecker`'s `/releases/latest` never sees it; the combined `trailpack.zip` app 0.15.0 reads is left there. App side: `data/TrailPack.kt` = **`TrailPacks`** (process scope via `TrailmapApp.packs()`, passed to `OverpassClient`): `filesDir/trailpack/state-<slug>.zip`, `packs.json` (the **selection** + installed asset dates + last check), `index.json`. **Coverage is across installed states together** — downtown KC's tile (-379_156) is inside neither Kansas nor Missouri alone — a tile counts when a 5×5 grid of points over it all fall inside some installed state's outline (or it's in a pack's `covered`). `OverpassClient.elementsFor` answers any circle centred in a covered tile from the packs before memory/disk/network (even `forceRefresh`), filtering to the radius like `around:` and de-duping by (type,id) across tiles and states. `offline/TrailPackWorker.kt` (WorkManager, `APPEND_OR_REPLACE`) refreshes the index, downloads chosen states that are missing or older than the release, re-reads the selection each pass, prunes unchosen ones; runs from `TrailmapApp.onCreate` when a chosen state is missing, the index is absent, or 24 h have passed, and on every add. `install()` validates the zip + schema before swapping. **Selection**: first run picks the state(s) containing the device location (`chooseDefaultStates`); the 0.15.0 combined pack becomes the selection {kansas, missouri} and is deleted once both have their own packs (or as soon as either is removed). UI: Offline screen card → **Trail data** screen (`ui/StatesScreen.kt`: On this phone / Near the map / All states, Add / Remove / refresh), and a **map offer** ("Get Nebraska trails on this phone", `ui.packSuggestion`) when the map is over an uninstalled state (dismissable per session). Measured on the emulator: pan loads 0.4-0.8 s end to end, MTB with park names 1.7 s — against ~35 s + 13 s from Overpass. Bump `PACK_SCHEMA` (script) and `TrailPacks.SCHEMA` together when the layout or filters change; older apps then ignore new packs and fall back to Overpass. Tests: `TrailPackTest` (zero network inside packs; border tile needs both states; legacy migration; remove; truncated download; wrong schema).
- **Trails: OSM Overpass API** (`https://overpass-api.de/api/interpreter`, POST, **must set a User-Agent**).
  ALL-mode query = `highway` in path/cycleway/track/bridleway + footway **excluding** `footway=sidewalk|crossing|traffic_island|access_aisle` (critical — without the sidewalk exclusion a 6 km KC pull is ~25k ways, ~96% sidewalks; with it, ~750), and **`["name"]` on every clause**. The name filter matters as much as the sidewalk one: `filtered` drops every "Unnamed path" before anything is drawn, so unnamed ways were downloaded, parsed and retained only to be discarded — an 8 km KC pull goes from **4,034 ways / 3.13 MB to 277 ways / 416 KB** with no visible difference. If unnamed connectors are ever wanted on the map, that filter and this one come off together. `out geom;` inlines coordinates.
- **MTB-mode query** = `way[mtb:scale]` + `way[highway=path][bicycle=designated][surface~ground|dirt|…]` + `relation[route=mtb]`, all `out geom;`. Relations carry the named loops (Wudchuk Run, the Augie phases); the parser builds one trail per relation from its member-way geometry and dedupes member ways out of the standalone-way list. A second **park-polygon query** runs (sequentially — concurrent requests trip the per-IP 429) for system naming.
- **On-device cache:** `OverpassClient(cacheDir)` caches raw Overpass responses under `<cacheDir>/overpass/<CACHE_SCHEMA>_<kind>_<lat>_<lon>_<radius>.json` (currently **v4**; bump `CACHE_SCHEMA` when the queries or the key format change). kind ∈ all/mtb/parks; the center is **snapped onto a grid of ~radius/6**, and lookup is **coverage-based, not exact-key** — `coveringCache()` reuses any stored circle that contains the requested one to within `COVER_SLACK` (15% of the radius) — since Overpass `around:` makes a wider pull a superset of a narrower one centred inside it. The slack matters: strict containment meant a *same-radius* circle only ever matched a request at exactly its centre, so a warm restart a few hundred metres away still went to the network. `TrailsResult` therefore carries the **served centre as well as the served radius**, and the ViewModel records both, so the coverage gate reasons about the circle the data actually occupies and refetches once the map genuinely leaves it. Without that the cache could only ever hit an identical centre-and-radius, so a downloaded area bought nothing and a small pan was a fresh download of data already on the device. `fetchTrails` returns a `TrailsResult` carrying the radius actually **served**, and the ViewModel stores *that* as `loadedRadiusMeters` — recording what was merely *asked* for made the app think it held 5 mi when it held 15, and refetch far sooner than it needed to. The wider set is kept, not trimmed: the **map draws everything cached** (so panning inside it needs no refetch) while the **Trails list uses `ui.listed`**, which narrows `filtered` to the radius chip. A covering entry is served **immediately even when expired**, with a background refresh scheduled behind it (`scheduleRefresh`) — trail geometry barely changes week to week, and making the user watch a spinner for data already on the device was the whole complaint. **7-day TTL**, pruned once per process. On top of that an **in-memory parse cache** (`memo`, LRU bounded to 8 MB of source JSON) skips both the file read and the deserialize — that's what takes a revisited area from ~1.5 s to ~0.3 s, since parsing a 3 MB response dominates a disk hit. Only the parsed *elements* are memoized, not finished `Trail`s, so each trail's distance is still measured from the current center. On network failure (429/offline) it falls back to a **stale** cached copy and sets `lastServedStale`, which the map surfaces as "Offline — showing saved trails". The my-location **FAB force-refreshes** (bypasses cache); everything else is cache-first — including startup (`bootstrap()`), which used to force-refresh on every return to the Map tab.
- **Overpass rate-limiting:** pan-triggered fetching is exactly the pattern that earns a per-IP 429, so `post()` enforces a **1.2 s minimum gap** between requests actually put on the wire and a **30 s cooldown after a 429 — per mirror, never global**. Only 429 counts: Overpass answers a momentary overload with **502/504** ("Dispatcher_Client::request_read_and_idx::timeout — the server is probably too busy"), which is transient and must fall through to the next mirror. Treating 504 as rate-limiting once locked out every mirror for 30 s and left the map blank behind a wrong banner. Loads retry once after 2.5 s on a failure that was neither a 429 nor a timeout. OkHttp's `connectTimeout` is 15 s and `readTimeout`/`callTimeout` are **45 s** — deliberately tight for a map that reloads as you pan, since a healthy mirror answers a named-way query in 2-20 s and `overpass.private.coffee` has been seen taking 40 s to return a 500. The mirror that last succeeded is tried first and is **persisted in `Prefs`**, so a dead primary isn't re-tried on every cold start — on-device that block cost ~3.7 s per launch before failing over. **Public Overpass instances hand out temporary per-IP blocks** and pan-loading is exactly the traffic shape that earns one — `overpass-api.de` blocked this network during development (connection refused, status endpoint unreachable) and the app carried on via `maps.mail.ru`. `MIN_NETWORK_GAP_MS` is 3 s and the coverage gate (`EDGE_SLACK` 0.4, `MIN_DRIFT_FRACTION` 0.35) is the main lever on request volume. MTB mode reuses the last park polygon set while the map stays within half its radius, halving its per-pan cost.
- **Overpass resilience:** `OverpassClient.post()` **hedges** across mirrors — `overpass-api.de` → `maps.mail.ru` → `overpass.private.coffee`, the last winner first. If a mirror hasn't answered in `HEDGE_AFTER_MS` (8 s; `HEAVY_HEDGE_AFTER_MS` 25 s for the MTB and park queries) the next is asked in parallel; the first good answer wins and the rest are cancelled ("dropped" in Diagnostics); a mirror that fails outright hands over at once. It used to try them sequentially with a 45 s call timeout inside a 25 s load budget, so a stalled preferred mirror sank every load and the others were never asked. `MirrorHedgingTest` covers this against local sockets. **Declared `[timeout:N]` matters:** Overpass admits a query against the time it declares, so the queries declare close to what they need (ALL 45, MTB 60, parks 45). Measured from KC: the 40 km MTB query was accepted 3/3 declaring 45 s (32–38 s, 2.75 MB) and 504'd on half its tries declaring 180 s. MTB loads get `MTB_LOAD_BUDGET_MS` (90 s) because that query simply takes ~35 s; ALL keeps 25 s. MTB shows trails as soon as the trail query lands (`fetchTrails(withParks = false)` → `TrailsResult.parksPending`) and the ViewModel then fetches park polygons (~13 s, 2.2 MB) to name the systems. Heavy public-API use is the reason the follow-ups suggest self-hosting Overpass eventually.
- **Uses:** walk / bike / **horse** (`UseType.HORSE`, "Horseback"): `highway=bridleway` unless `horse=no`, or `horse=yes|designated|permissive` (`horseAllowed`). An untagged path is *not* assumed to allow horses. KS+MO have ~350 named horse-legal trails (e.g. Longview Lake Horse Trail). Horse icon is Phosphor's `horse-fill` (MIT) in `ui/HorseIcon.kt` — Material has none. **Purple = horse trails, not every horse-legal trail.** A horse trail (`isHorseTrail`) is a bridleway or `horse=designated` path **that bikes aren't allowed on** (walkers may be); multi-use trails that merely allow horses keep their surface colour — in KS+MO that's 131 named horse trails (Longview Lake Horse Trail, Appaloosa Equestrian Trail) vs 213 horse-legal multi-use (Flint Hills Trail, the Katy Trail's horse sections). Per piece: `Trail.horseTrailPaths` parallel to `paths`, written as a `horse` feature prop by `trailsFc` (ALL mode only) and checked first by `surfaceColorExpr` (`HORSE_LINE_COLOR` light #7B1FA2 / dark #CE93D8, legend "Horse trail"). `Trail.horseTrail` (≥ half its length) drives the **Filters → "Horse trails: Show / Hide / Only"** row (`HorseTrailFilter`, `ui.horseTrails`), the purple bar on list rows (`HorseTrailColor`) and "Horse trail ·" on the detail screen. The Use chips (Walk/Bike/Horse) still mean "allowed", so Horse finds everywhere you can ride. MTB mode keeps difficulty colours.
- **Surface buckets:** raw OSM `surface=*` → PAVED / GRAVEL / DIRT / UNKNOWN (`SurfaceType.fromOsmSurface`), with a highway-type fallback when untagged (`inferFromHighway`: cycleway→paved, track→gravel, path/bridleway→dirt). ~70% of cycleways carry a real surface; paths are spottier.
- **Riding order (`data/TrailRoute.kt`).** A named trail is many OSM ways in response order and arbitrary direction. Flattening them (the old `trail.allPoints` profile) measured every jump between unrelated pieces: the Gary L. Haller Trail is 81 ways / 16.26 mi but flattened measured 135.4 mi, the chart axis ran past 116 mi, the climb read +5,265 ft and scrubbing sent the marker back and forth. `TrailRoute.order(paths)` splits ways at shared vertices, snaps way ends within 30 m onto another way, bridges remaining gaps with a minimum spanning tree of straight "gap" edges, takes the graph's end-to-end trunk (double Dijkstra), walks it depth-first (spurs first) from its south/west end, then sorts runs by where they meet the trunk. Gaps and backtracks start a new run and are never counted as distance. Used by the elevation profile (`ElevationClient.profile(trail.paths)`), the detail preview's start/end dots, and Directions. Climb is a 3-point median (the DEM reads the creek under a bridge, not the deck) with a 1 m dead band; Haller now reads +278 / −406 ft. `ElevPoint.gapBefore` lifts the chart line across gaps. Test: `TrailRouteTest` incl. the real Haller geometry fixture.
- **Elevation: Open-Topo-Data `ned10m`** (`https://api.opentopodata.org/v1/ned10m?locations=lat,lon|...`), max 100 pts/req, ~1 req/sec — the client chunks + throttles. USGS EPQS (`https://epqs.nationalmap.gov/v1/json`) is the authoritative US spot-check fallback (~897 ft at KC center).

## UI snapshots (Paparazzi)
Every screen is a thin `XScreen(vm)` wrapper plus a stateless `XContent(ui, callbacks)` (map: `MapOverlays`), so **Paparazzi 1.3.5** (test-only plugin) renders them on the JVM with sample Kansas City data: `cd mobile && ./gradlew :app:recordPaparazziDebug` → `app/src/test/snapshots/images/`. Tests are `test/.../snap/ScreenSnapshots.kt`; data in `Samples.kt` (real KC trail names, made-up geometry). MapLibre draws with native GL and can't render there, so map shots sit on a drawn `FauxMap` stand-in. Use this rather than the emulator for UI review — the emulator's starmap app steals the foreground and Overpass rarely answers over its network. Keep new screens split the same way.

## Build / run (emulator)
```bash
export ANDROID_HOME=/home/spider/tools/android-sdk
cd mobile && ./gradlew :app:assembleDebug          # ~1-2 min
$ANDROID_HOME/platform-tools/adb install -r app/build/outputs/apk/debug/app-debug.apk
$ANDROID_HOME/platform-tools/adb emu geo fix -94.5786 39.0997   # pin GPS to KC (lon lat)
$ANDROID_HOME/platform-tools/adb shell am start -n com.trailmap/.MainActivity
```
AVD: `trailmap_pixel9a` (android-35 x86_64, pixel_7 profile — SDK has no pixel_9 device def).
The `default` (non-Google) system image has **no Play Services**, so fused location throws → `Locator` falls through to `LocationManager` (`adb emu geo fix LON LAT`), then to Kansas City. **Gotcha:** another app on this AVD (`com.starmap.app.debug`) grabs foreground on location updates and can leave a sticky mock GPS fix that `emu geo fix` won't override. Fix = **cold boot** the emulator (`adb emu kill` → relaunch with `-no-snapshot`), which clears the wedged location state and doesn't auto-start starmap; then `emu geo fix` to KC works (or `Locator` falls back to KC if no fix). Note a cold boot can revert uninstalled-but-uncommitted app state — **reinstall the APK after cold-booting**. (All a non-issue on a real Pixel 9a.)

## Known follow-ups / ideas
- Outside the installed states, pan-loading still hits the public Overpass API. The brakes are the coverage gate, the debounce, request cancellation, the minimum gap, the 429 cooldown, and the "Load trails as I pan" switch. Near an uninstalled neighbour, circles centred in a tile that isn't fully inside installed states still go to Overpass.
- Map tap uses queryRenderedFeatures + a nearest-trail peek-card fallback.
- The Trails list header still reads "within N mi" from the radius *chip*, which is a floor — a zoomed-out pan may have fetched a wider circle than the chip says.
